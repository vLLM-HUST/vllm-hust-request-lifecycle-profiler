\begin{abstract}
LLM serving slowdowns are often diagnosed from aggregate latency and scattered
logs, making it difficult to distinguish causal bottlenecks from correlated
symptoms. This draft studies request lifecycle profiling: representing each
request as an ordered timeline across tokenization, queueing, prefill, decode,
streaming, and cleanup, then attributing the dominant bottleneck under
controlled fault injection. The current artifact contains the trace schema,
attribution skeleton, deterministic synthetic fault-injection harness, tests,
NPU6 preflight contract, warmup-controlled client-observed trace probe,
experiment plan, and claim ledger. It does not yet claim internal vLLM
scheduler/KV tracing, measured diagnosis accuracy, or internal runtime tracing
overhead.
\end{abstract}

\keywords{LLM serving, observability, profiling, causal diagnosis}

\maketitle

\section{Problem}

Aggregate TTFT and TPOT report symptoms, not causes. A request may be slow
because of queueing, prefill saturation, KV allocation, decode jitter, slow
streaming, or cleanup stalls. We study whether lifecycle traces can become
auditable causal evidence for optimization work.

\section{Key Idea}

Each request emits ordered lifecycle events. The profiler converts complete
event pairs into stage spans and attributes the dominant bottleneck using an
explicit rule set that can be validated by fault-injection ground truth.

\section{Design Scope}

The first implementation provides trace primitives, schema coverage checks, and
deterministic attribution logic. The no-NPU harness covers tokenizer delay,
queueing, prefill, decode, KV pressure, streaming backpressure, and cleanup
stalls with known ground truth. The NPU6 preflight contract specifies the
endpoint, model path, authentication, Ascend runtime root, device ownership, and
trace export schema required before existing-server probes can support
client-observed online evidence. The current NPU6 probe records request
preparation, HTTP send, first streamed chunk, stream completion, and cleanup
from the probe process. The latest runtime hook path also records internal
OpenAI entry, scheduler, prefill, first-token, decode, stream-handoff, and
cleanup events through a repo-local bridge when trace export is enabled.

\section{Evaluation Plan}

The evaluation will compare the profiler against raw logs, simple stage timers,
manual diagnosis, and profiler reports with causal rules disabled. Metrics
include attribution accuracy, false positives, false negatives, tracing
overhead, event coverage, and root-cause diagnosis time. Internal runtime-hook
evidence is now available for the NPU6 smoke workload; controlled live faults
with known ground truth remain required before claiming runtime diagnosis
accuracy.

\section{Current Evidence Boundary}

No-NPU trace tests and a deterministic synthetic fault-injection matrix are
currently supported as \texttt{simulation/model} evidence. The latest synthetic
matrix reports seven of seven correct attributions with zero false positives,
zero false negatives, and zero missing-event rate
(Table~\ref{tab:synthetic-faults}). This validates the deterministic span and
attribution logic under known ground truth before interpreting live traces.

The live NPU6 evidence is narrower. The repo-local preflight is READY, and a
warmup-controlled existing-server probe records one warmup request plus 12
measured streaming requests on the managed NPU6 endpoint. All measured requests
succeed, and the probe emits 117 client-observed lifecycle events across nine
stage names. Table~\ref{tab:npu6-trace} summarizes the generated paper asset.
A matched proxy-overhead suite then replays the same 12-request shape with
client-side event construction disabled and enabled. Trace mode emits 117
events and changes TTFT p95 by +4.07\,ms relative to no-trace
(Table~\ref{tab:npu6-overhead}). This is evidence about the probe process, not
internal runtime hook overhead.

The internal runtime-hook path is now measured separately. A matched NPU6 smoke
pairs hook-disabled serving with low-overhead hook-enabled serving while keeping
the same request shape. The enabled run writes 117 runtime JSONL events and
recovers 13 of 13 complete request chains, each with all nine lifecycle stages.
After replacing per-event file open/write/close with a persistent append file
descriptor in the trace sink, the hook-enabled run changes TTFT p95 by
-2.14\,ms and latency p95 by +0.93\,ms relative to the disabled baseline
(Table~\ref{tab:npu6-runtime-hooks}). This is still a small smoke result, so it
does not establish TPOT, memory, or broad-workload overhead.

The same trace can also be reduced into a client-visible stage diagnosis. The
derived diagnosis pass computes per-request spans and coverage from the checked
in NPU6 proxy events. It reports zero missing-event rate and attributes all 12
measured requests to the decode-visible span, with decode-proxy p95 of
98.75\,ms and prefill-proxy p95 of 85.50\,ms
(Table~\ref{tab:npu6-diagnosis}). This does not prove that the internal runtime
root cause is decode; rather, it gives a concrete hypothesis that internal
scheduler, KV, prefill, and decode hooks must confirm or overturn.

We also added a controlled client-visible slow-stream probe. The probe keeps
TTFT low but intentionally waits 80\,ms while reading each streamed chunk and
uses a streaming-proxy span boundary. All four measured requests succeed; TTFT
p95 remains 81.14\,ms, while end-to-end latency p95 rises to 5208.20\,ms. The
derived diagnosis switches from the normal decode-visible hypothesis to
streaming for 4/4 measured requests, with streaming-span p95 of 5127.09\,ms
(Table~\ref{tab:npu6-slow-stream}). This is a controlled client-probe
backpressure result, not an internal runtime streaming claim.

The next NPU6 batch runs the same slow-stream fault with the hook-enabled
runtime active. The client-visible diagnosis again attributes 4/4 measured
requests to streaming, with latency p95 of 5334.74\,ms and streaming-span p95
of 5126.99\,ms. At the same time, the internal runtime hook writes 45 JSONL
events over 5/5 complete request chains, each containing the nine expected
lifecycle stages. This closes the hook-coverage gap during a known fault, but
it is still not an internal-only diagnosis accuracy result: the injected
client-side slow read remains the ground-truth fault and the runtime trace is a
coverage/correlation artifact for this batch.

We then add a second hook-enabled controlled fault using the structured-agent
decode workload with 128 requested output tokens. This run succeeds for 4/4
measured requests and switches the client-visible diagnosis to decode for 4/4
requests. The decode span dominates with p95 1986.54\,ms, while streaming p95
stays at 0.0\,ms. The internal runtime hook again records 45 events over 5/5
complete chains. Two attempted long-context candidates failed before usable
attribution under the current 4096-token service profile; those directories
are retained as boundary evidence rather than diagnosis results.

The third hook-enabled fault keeps the same runtime-entering structured-agent
prompt but reduces requested output to four tokens. This run succeeds for 8/8
measured requests and switches the client-visible diagnosis to prefill for
8/8 requests: prefill-span p95 is 133.66\,ms, decode-span p95 is
36.70\,ms, and streaming p95 remains 0.0\,ms. The internal runtime hook records
81 events over 9/9 complete chains. This closes the first valid
prefill-dominant live-fault coverage gap, but it is still not an internal-only
root-cause accuracy claim.

Finally, we sweep measured concurrency 1/2/3 on the same structured-agent
shape with eight requested output tokens. All 27 measured requests succeed,
and the combined runtime hook trace records 270 events over 30/30 complete
chains. The sweep exposes a candidate prefill/KV or scheduler boundary rather
than a simple throughput curve: concurrency 1 is mostly decode-dominant
(7 decode, 2 prefill) with TTFT p95 163.30\,ms, concurrency 2 switches to
8/9 prefill-dominant requests with a severe TTFT p95 of 12299.08\,ms and
prefill-span p95 of 12298.88\,ms, while concurrency 3 is 9/9 prefill-dominant
but has TTFT p95 131.61\,ms. This is currently a client-visible anomaly with
runtime-hook coverage; the next step is to correlate it with internal
scheduler, batch-transition, graph-capture, or KV-allocation signals.

Table~\ref{tab:npu6-decision-impact} restates the same evidence as an
optimization decision aid. Ordinary request timers can show that latency is
large, but lifecycle spans determine which next experiment should run: normal
proxy traces motivate internal decode/prefill validation, while the slow-stream
proxy should first test streaming backpressure isolation before tuning compute
stages. This is the current artifact's strongest evidence that causal traces
change the optimization queue, while still remaining inside the client-visible
proxy boundary.

\section{Claim Boundary}

The current evidence supports trace schema feasibility, synthetic attribution
coverage, live client-observed lifecycle export, derived proxy-stage diagnosis,
controlled client-visible slow-stream discrimination, a narrow client-probe
event-construction overhead smoke, full internal lifecycle capture on a small
NPU6 smoke workload, bounded runtime-hook overhead on that smoke, runtime-hook
coverage during known slow-stream and decode-heavy faults, and a derived
decision-impact view over the same proxy traces. The new prompt-heavy
low-output fault adds a valid prefill-dominant live case with runtime-hook
coverage, and the concurrency sweep adds a concrete non-monotonic
prefill/TTFT tail to explain with deeper runtime signals. The decision-impact
table is
not a new online measurement: it summarizes which follow-up optimization
experiment each proxy diagnosis justifies. The artifact does not yet support
claims about internal-only diagnosis accuracy on live faults, memory overhead,
TPOT overhead, broad workload generality, or root-cause time improvement. Those
claims require internal correlation for the concurrency-2 anomaly, causal-rule
comparison against raw timers, TPOT/HBM overhead evidence beyond the smoke
workload, and a larger workload matrix.
